# PULSE P0.4.18 — Server Execution Claim Store

## Objetivo

Definir y verificar el primer adapter server-side real para las execution claims de PULSE.

P0.4.17 estableció el contrato:

`PulseExecutionClaimStore`

con:

- `atomic: true | false`;
- single-use por `approval_id`;
- fail-closed cuando una mutación crítica no dispone de atomicidad.

P0.4.18 añade una implementación server-side persistente.

## Implementación

Archivo:

`src/server/DigitalBoostPulseServerExecutionClaimStore.ts`

Características:

- Node.js server-side;
- persistencia en filesystem;
- creación atómica del claim;
- namespace aislado por tenant;
- supervivencia entre instancias del proceso;
- no requiere dependencia externa;
- reutiliza el contrato canónico de PULSE.

La operación crítica no usa:

`exists() -> write()`

porque ese patrón tiene una ventana de race condition.

En su lugar:

1. se escribe el payload completo en un archivo temporal;
2. se crea el enlace final exclusivamente mediante `linkSync()`;
3. si el destino ya existe, la claim ya fue consumida.

## Tenant isolation

El directorio de almacenamiento se deriva de:

`SHA-256(tenantId)`

y el nombre del claim de:

`SHA-256(approval_id)`

Por lo tanto:

`tenant A + approval X`

y

`tenant B + approval X`

ocupan namespaces diferentes.

Esto evita que una misma cadena `approval_id` produzca colisiones entre tenants.

## Límite de esta implementación

Este adapter garantiza atomicidad en el filesystem compartido por los procesos que acceden al mismo almacenamiento.

No debe interpretarse como garantía distribuida para:

- múltiples servidores;
- múltiples hosts;
- almacenamiento de red con semántica incierta;
- clusters sin filesystem compartido correctamente coordinado.

La implementación de producción distribuida prevista para la siguiente etapa debe usar una base de datos con una restricción única equivalente a:

`UNIQUE (tenant_id, approval_id)`

y una operación transaccional/idempotente.

## Integración

P0.4.18 todavía no conecta el adapter directamente con `executePulseAction()` del navegador.

La razón es arquitectónica:

- `executePulseAction()` actual es síncrono;
- el navegador utiliza `localStorage`;
- convertir el executor actual en async sería un cambio de frontera mayor;
- exponer un endpoint público de claims sin una capa de autenticación introduciría una nueva superficie de seguridad.

La integración correcta debe ocurrir en el boundary de ejecución server-side.

Flujo objetivo:

`PULSE -> POLICY -> APPROVAL -> SERVER EXECUTION CLAIM -> MUTATION -> VERIFY -> ATTESTATION -> AUDIT`

## Verificación

P0.4.18 cubre:

- atomicidad entre dos stores independientes;
- persistencia entre recreaciones del store;
- aislamiento por tenant;
- single-use;
- validación de tenant.

`BUILD PASS` no sustituye la integración final del executor server-side.
